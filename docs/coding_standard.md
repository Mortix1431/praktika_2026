# Правила корпоративного стандарта программирования

Справочный документ. Все практические задания выполняются с соблюдением этих правил.

## 1. Административная часть

- **a.** Все требования настоящего списка могут иметь исключения, которые рассматриваются в индивидуальном порядке в каждой конкретной ситуации.
- **b.** Все спорные ситуации о том, как можно и нельзя что-либо писать, в конечном итоге разрешаются старшим сотрудником в приказном порядке.

## 2. Базовые моменты

- **a.** Запрещено «изобретать велосипед» — все базовые утилитарные функции и алгоритмы уже реализованы; если они не видны, спроси у старшего.
- **b.** Любая часть кода программного проекта должна стремиться к использованию принятых в проектах типов данных. Запрещено вводить свои пространства аналогичных по функционалу типов (к примеру, свои строки, контейнеры).
- **c.** Запрещено использовать макросы и псевдонимы для базовых простых типов.
- **d.** При введении новых утилитарных методов и алгоритмов нужно обеспечить их общую доступность и подробное описание (документирование в комментариях, в сложных случаях — отдельным документом).
- **e.** В код должен закладываться функционал диагностирования и тестирования, доступный в коммерческом приложении (использование утилиты InDebMon).

## 3. Работа с программным кодом

- **a.** Вся работа выполняется в Microsoft Visual Studio.
- **b.** Весь рабочий код должен регулярно выкладываться в общую базу (не реже раза в неделю).
- **c.** Не реже раза в неделю нужно синхронизировать локальную копию кода с базой.
- **d.** При разрешении конфликтов в коде нужно за основу брать версию с сервера.

## 4. Оформление кода

- **a.** Методы и функции в листинге должны иметь комментарии-разделители (для всех алгоритмических языков!) на русском языке.
- **b.** Логические блоки кода должны разделяться пустыми строками.
- **c.** Реализации методов одного класса должны находиться рядом.
- **d.** Члены-данные классов должны иметь префикс имени `m_...`, статические — `s_...`.
- **e.** Глобальные данные должны иметь префикс в имени `g...`.
- **f.** Запрещается использование сложных, «красивых», «крутых» выражений. (Если твой сосед за несколько секунд не понимает смысл написанного «красивого» выражения — упрости его.)
- **g.** В качестве отступов в коде используется табуляция.
- **h.** Комментарии:
  - **i.** Комментарии должны описывать принцип работы комментируемого блока.
  - **ii.** Функции, алгоритмы в общем доступе должны содержать исчерпывающее функциональное описание в комментариях.
  - **iii.** При исправлении ошибок нужно указывать номер ошибки в соответствующей базе.
  - **iv.** При исправлении ошибки в чужом коде нужно также указать ник автора исправления и дату.

## 5. Техника программирования

- **a.** Исключения:
  - **i.** В C++ использование явного бросания исключения запрещено. Для индикации ошибочной ситуации использовать коды возврата.
  - **ii.** В C# запрещено генерировать исключения в реализации общедоступных интерфейсов. Если таковые всё же генерируются, они все должны быть явно перечислены в описании.
  - **iii.** В C# нужно оборачивать в `try..catch` методы, содержащие составные операторы с множеством обращений, каждое из которых может привести к сбою.
- **b.** Запрещено реализовывать рекурсию классическим способом: вызов самого себя.
- **c.** Любой итерационный алгоритм должен иметь защиту от зацикливания.
- **d.** Свести к нулю прямую работу с динамической памятью (C++).
- **e.** Работа с динамически создаваемыми объектами должна выполняться с использованием указателей-шаблонов, автоматически реализующих своевременное уничтожение объекта.
- **f.** Сложные типы данных передавать/возвращать через ссылки или указатели.
- **g.** Шаблоны:
  - **i.** STL запрещён.
  - **ii.** Шаблоны запрещено использовать, если код в шаблоне можно реализовать с использованием системы наследования (в том числе виртуального).
  - **iii.** Запрещено использовать шаблоны в базовой архитектуре программного проекта (за исключением контейнеров).
- **h.** Все строковые ресурсы, видимые пользователю любым способом, должны локализовываться сразу в момент добавления такового ресурса в код (техника локализации описана в отдельном документе).
- **i.** Реализация методов и функций должна начинаться с проверки входных аргументов.
- **j.** Все переменные-члены классов должны инициализироваться.
- **k.** Проверять указатели на валидность перед обращением.
